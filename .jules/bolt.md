## 2026-11-07 - Failed: Parallelizing speechmix.chain.deess via ThreadPoolExecutor
**Learning:** `speechmix.chain.deess` already used `ThreadPoolExecutor(max_workers=1)` to pipeline the per-chunk low-pass filter (sosfilt, main thread) with the numba gain kernel (worker thread). Attempts to increase to `max_workers=2` (133 ms vs 111 ms for 1 minute of stereo 48 kHz audio) or remove the thread pool entirely (125 ms vs 111 ms) both regressed. The per-chunk tasks (~1–3 ms each) are too short for additional thread pipelining to overcome thread management overhead; `max_workers=1` was already the sweet spot.
**Action:** `ThreadPoolExecutor(max_workers=1)` in `deess` is intentionally optimal; do not change. Future parallelism gains in this function would require restructuring to submit multiple kernels ahead (overlapping kernel k+1 with kernel k), which is unsafe because the `follow` follower state is shared between consecutive kernels.

## 2026-11-06 - Eliminating Intermediate Array Allocations in envelope_at with bisect
**Learning:** `speechmix.envelopes.envelope_at` interpolates volume envelope curves at a scalar timestamp `when`. Previously, each scalar query rebuilt a full list of timestamps from `points` via list comprehension (`times = [t for t, _ in points]`) and passed it to `np.searchsorted`. For a Python list of `(t, v)` points, this incurred an $O(N)$ heap allocation and Python list + NumPy array boxing overhead for every single point query. Replacing `np.searchsorted` with the standard library `bisect.bisect_left(points, when, key=lambda p: p[0])` performs the binary search in $O(\log N)$ time directly over the existing list with zero intermediate allocations. Across realistic envelope point counts (e.g. 200 points for a multi-span track), querying the envelope improved by ~19x (~20.2 µs -> ~1.05 µs per query; up to 63x on 1000 points) while remaining exact.
**Action:** When performing scalar lookups or point interpolations over sorted Python list structures, avoid extracting temporary key lists or delegating to NumPy search functions that convert Python lists to arrays; use standard library `bisect` with a `key` selector to achieve $O(\log N)$ lookup with zero allocation overhead.

## 2026-11-05 - Direct float32 Linear Blending in speechmix.mixlaw
**Learning:** `speechmix.mixlaw.mix_blend` cross-fades raw and wet float32 audio buffers based on dxRevive's non-linear mix curve. It previously upcast both inputs to float64 (`raw.astype(np.float64)` and `aligned.astype(np.float64)`), which allocated two full 64-bit temporary arrays and a 64-bit sum array before downcasting back to float32. For standard multi-channel audio buffers (e.g. 30 seconds of stereo 48 kHz audio), this ballooned peak allocation from ~22 MB to ~44 MB (2.0x overhead) and took ~32.2 ms. Blending directly in float32 with an in-place addition (`np.multiply(raw, w_dry, out=out); out += w_wet * aligned`) and fast-pathing exact identity endpoints (`mix == 0.0` and `mix == 1.0`) avoids the 64-bit allocations and runs ~3.1x faster (~10.3 ms vs ~32.2 ms) with identical float32 output precision.
**Action:** When performing linear combinations on float32 audio buffers where the destination type is float32, avoid upcasting to float64 for intermediate arithmetic unless precision bounds require double precision; scale and accumulate into preallocated buffers to halve memory usage and cut computation time.

## 2026-11-05 - Vectorizing Run-Length Interval Extraction in speechmix.masks
**Learning:** `speechmix.masks.runs()` generates `(start, end, value)` intervals from boolean/integer timeline mask arrays. The endpoints were originally indexed element-by-element in a Python list comprehension (`[(int(bounds[i]), int(bounds[i+1]), int(values[bounds[i]])) for i in range(bounds.size - 1)]`), which repeated scalar indexing, boundary checks, and `int()` boxing per segment. By slicing the vector bounds array once (`starts = bounds[:-1]`, `ends = bounds[1:]`, `vals = values[starts]`) and using `.tolist()` combined with `zip(..., strict=True)`, the extraction runs ~3.5x-4.0x faster without changing return types or tuple layouts.
**Action:** When extracting run spans or intervals from transition indices in NumPy arrays, slice the array bounds into vectorized start, end, and value sub-arrays and convert them via `.tolist()` rather than indexing individual elements in Python loops.

## 2026-11-04 - Vectorizing Grid Search in nhsx.fades
**Learning:** `nhsx.fades.long_segments()` performs grid search (`_fit_two` and `_fit_run`) to find optimal raised-cosine `<Fade>` ramp parameters matching volume curves. The inner search originally looped over combinations of candidate start, middle (junction), and end times in Python, executing individual NumPy ufuncs (`clip`, `cos`, `log10`, `max`) per combination (~90,000 inner iterations in `_fit_two` for a typical 8-second rise). Because the error calculation on the second segment depends only on the junction step `m` and endpoint step `e`, all candidate endpoints `e` can be evaluated simultaneously in a 2D broadcasted array across time points. This reduces the number of NumPy array evaluations from ~90,000 to $O(S)$ vectorized operations without altering the search space or math.
**Action:** When performing 1D parameter grid search over interval endpoints, check if inner segments decouple from earlier loop variables. Vectorizing the candidate bounds in 2D array slices eliminates Python loop interpretation and function dispatch overhead.

## 2026-11-02 - Decouple Independent Multi-Ramp Curve Fitting Searches
**Learning:** In piecewise curve-fitting algorithms over time-ordered grids such as `nhsx.fades._fit_two`, the breakpoint partitions input samples into independent ramp segments. Evaluating each ramp's error separately avoids recomputing full-window errors for every parameter combination. An earlier implementation measured ~17x faster (~3.88 s to ~0.20 s) on an 8.5 s rise; `main` now vectorizes endpoint candidates as well.
**Action:** For multi-ramp fits, partition at the junction and calculate each segment's error independently before combining the errors; vectorize candidate bounds where possible.
